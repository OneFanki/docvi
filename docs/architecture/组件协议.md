## 通用约定

- 组件由渲染层的组件注册表按 kind 装载（`packages/renderer-core/src/components.ts` + `apps/desktop/src/renderer/src/lib/component-registry.ts`，通用组件来自预设包 `plugins/base`）；Markdown 正文直接写 `<at-组件名 data-key="键"></at-组件名>`，**无需**在页面导入；
- 组件不包大段 Markdown——正文在组件之间流动；
- 页面数据放 frontmatter 的 `components` 段（见下节），**零 script setup、零业务 JS**；
- 代码明文直接写进数据段（旧 `?raw` 引入写法可用 `scripts/migrate-declarative.mjs` 一次性迁移）；
- 样式只消费 `--at-*` token，明暗双色由 `.dark` 自动切换，不写死颜色；
- **全屏 / 覆盖层的控件必须避让窗口按钮**：窗口按钮由系统画在标题栏那一条上
  （Windows 右上角是最小化/最大化/关闭，macOS 左上角是红绿灯）。全屏覆盖层
  从窗口顶端铺下来时，它自己的顶栏控件会落进同一条带里——最右的「关闭」会被
  窗口的 ✕ 盖住，点下去关的是窗口而不是覆盖层。统一做法：顶边让出
  `var(--at-overlay-top, 0px)`（`packages/renderer-core/src/styles/theme.css`
  定义，值等于标题栏高度，纯浏览器环境回落 0）。两种写法都合规：
  铺满型（图片 / 大图查看）用 `inset: 0` + `padding-top: var(--at-overlay-top)`，
  居中模态型（流程图 / 状态机 / 表关系图）用
  `inset: calc(var(--at-overlay-top, 0px) + …) … …`。
- 类型定义随组件包：`plugins/base/src/components/types.ts`。

## 声明式数据格式（`components` 段）

组件全部是 props 驱动的数据型组件——数据放 frontmatter 的 `components` 段（YAML），正文用 `at-` 前缀的自定义元素引用，**零 script setup、零业务 JS**（任何标准 markdown 渲染器可读）：

```yaml
---
title: 页面标题
components:
  orderEndpoints: # 键名任意（引用用）
    kind: endpoint-list # kind 决定组件（kebab-case，见组件清单映射）
    title: 订单接口清单 # 其余键与组件 props 同名，原样透传
    endpoints: [...]
---
正文：<at-endpoint-list data-key="orderEndpoints"></at-endpoint-list>
```

规则：

- `kind` = 组件清单表的名字转 kebab-case（如 `EndpointList` → `endpoint-list`、`TableTabs` → `table-tabs`）；
- 标签 = `at-` + `kind`，**必须写闭合标签**，`data-key` 指向 `components` 段的键；数据缺失时原位渲染占位提示，不白屏；
- 数据键与组件 props **同名**（`items`/`tables`/`endpoints`/`decisions`…）；`kind` 键本身不透传；
- 流式 YAML（`{ ... }` 行内写法）里的标量值**必须加引号**——`OrderBrief[]`、`decimal(10,2)` 这类含 `[]` `,` 的值不加引号会解析失败；
- 运行时：协议类型在 `packages/plugin-api`、清单校验在 `packages/plugin-runtime`；组件注册表与声明式数据桥在
  `packages/renderer-core/src/components.ts`（`ComponentRegistry`），宿主侧注册规则在
  `apps/desktop/src/renderer/src/lib/component-registry.ts`——桌面与容器共用同一套，差别只在 `window.docvi` 由谁提供；
  活样例见 `courses/component-showcase/chapters/03-契约与数据模型`。

> **以下各节的示例展示组件 props 名与数据形态**（`<组件名 :prop="var" />` 为书写示意）。
> 落到页面时的实际写法：数据进 frontmatter `components` 段（键名任意、值即各节数据），
> 正文写 `<at-kind data-key="键"></at-组件名>`。例：
>
> ```yaml
> components:
>   shell1:
>     kind: tutorial-shell
>     courseTitle: Vue 响应式系统
>     step: 1
>     stepTotal: 4
>     goals: [目标1, 目标2]
> ```
>
> 正文：`<at-tutorial-shell data-key="shell1"></at-tutorial-shell>`

## 1. `<TutorialShell>`

章节 H1 下方的页眉壳：所属课程名、第几步/共几步、学习目标。**不渲染 H1**（H1 由 Markdown 承担）。

```
<TutorialShell
  course-title="Vue 响应式系统"      # 课程名
  :step="1"                          # 本章是第几步
  :step-total="4"                    # 共几步
  :goals="['目标1', '目标2']"        # 读完本章你将理解…
/>
```

## 2. `<FlowDiagram>`

把「从入口到结果的一条主流程」渲染成纵向节点卡 + 带标注的连线；点击节点下钻详情。适用于线性/近线性流程（业务流程、数据管线等）。分支多、需自由布局的图暂不适用（P2 增强）。

```
FlowNode  = { id, label, note?, kind?: 'start' | 'step' | 'decision' | 'end' }
FlowEdge  = { from, to, label? }

<FlowDiagram title="构建管线" :nodes="nodes" :edges="edges" />
```

## 3. `<FileTree>`

静态教学目录树：目录可折叠，节点可带「职责说明」（右侧注释）。数据是嵌套数组。

```
TreeFileNode = { name, note?, kind?: 'file' | 'dir', children? }

<FileTree :data="tree" title="订单模块目录" />
```

## 4. `<CodeWalkthrough>`

带行号的分步代码讲解：每步高亮若干行（单行或闭区间）并显示讲解文字，上一步/下一步 + 步骤条。**steps 的行号必须与片段文件实际行号一致**（1-based 闭区间；改片段后同步改，曾有 off-by-one）。

```
WalkStep = { title, lines?: Array<number | [number, number]>, note? }

<CodeWalkthrough
  title="字节数格式化"                            # 可选
  filename="src/utils/format.ts"                # 可选：路径（mono 显示）
  source="教学片段：整理注释版"                    # 可选：出处徽标
  language="ts"
  :code="code"
  :steps="steps"
/>
```

## 5. `<CodeBlock>`

**无分步讲解**的普通代码块 + 文件名 + 出处徽标 + 一键复制。源材料（知识库音频教程）中每个代码块都带路径与出处，Markdown 原生围栏做不到，这是最常用的补充组件。

```
<CodeBlock
  title="字节数格式化"                              # 可选
  filename="src/utils/format.ts"                   # 可选
  source="教学片段：整理注释版"                      # 可选
  language="ts"                                     # 默认 ts
  :line-numbers="true"                              # 可选，默认 false
  :code="code"
/>
```

代码后的「为什么这样写」折叠讲解用原生 `<details>`（Markdown 直接写），与本块互补。

## 6. `<DecisionCard>`

关键设计决策：每条「决策 + 原因 +（可选证据）」。比 Markdown 表格更贴近教学语义，`kind: 'why'` 正向（✓）、`kind: 'avoid'` 反向避坑（⚠ 红）。

```
DecisionItem = { decision, reason, evidence?, kind?: 'why' | 'avoid' }

<DecisionCard title="构建管线的三个设计决策" :decisions="decisions" />
```

## 7. `<Checklist>`

验收 / 自检清单：可勾选 + 进度条 + localStorage 记忆（刷新/切页不丢）+ 一键重置。**同课程多个清单请给不同 `storageKey`**（缺省按 title 派生，同标题会共用同一记忆槽）。

```
ChecklistItem = string | { text, hint? }

<Checklist title="本章验收"
           :items="checks"
           storage-key="at:course:ch04" />
```

## 8. `<NextUp>`

每章结尾的「下一步阅读卡」：一个或多个入口，带徽标（推荐 / 可选 / 深入）与一句话简介；不带 `href` 的条目渲染为纯文本（指向仓库外素材等）。

```
NextUpItem = { label, href?, description?, badge? }

<NextUp :items="next" />
```

## 9. `<ApiContract>`

模块输入 / 输出契约与不变量：说清「调用方喂什么、模块吐给谁什么、两边都得保证什么」。面向**内部模块 / 函数边界**（服务模块 / 调度器 / 渲染状态这类契约的教学沉淀，不是 HTTP 端点——端点清单见 §21 EndpointList），比裸签名更能讲清时序与责任。不变量 `kind: 'must'` 正向保证（✓ 绿）、`kind: 'must-not'` 反向约束（红色警示）。

```
ApiPort       = { name, type, description }
InvariantRule = { statement, kind?: 'must' | 'must-not' }   // 也接受纯字符串

<ApiContract title="扫描器模块契约"
             :inputs="inputs" :outputs="outputs" :invariants="invariants" />
```

## 10. `<TableTabs>`

表设计场景的**唯一组件**（合并原 DataModel 能力）：一个页签一张完整字段表（字段名 / 中文名 / 类型 / 键 / 业务说明）；传 `relations` 时底部渲染**表间关系脚注**（`from → label → to`，不随页签切换、不随内容滚动）；只传一张表时不渲染页签栏（等价于「单表字段设计」形态）。适合 PRD 的数据设计与一切「表结构怎么设计」的说明——比「一行塞一张表」的汇总表好读得多。

行为约定（写内容时可直接依赖）：

- 组件高度上限 = 一屏可用高度（`calc(100vh - 8rem)`），表格在组件内部滚动——**横向滚动条始终在可视区内**（不用先把页面滚到底）；
- 页签栏固定在滚动区之外：**滚动内容时页签不动**；表头 sticky 吸顶；
- 全屏：原生 Fullscreen API，**整个组件（含页签栏）一起全屏**；嵌入式 iframe 等拿不到权限时退化为覆盖层，Esc 退出（全屏兜底逻辑与 §11 TableGraph 共用 `plugins/base/src/components/fullscreen.ts` 的 `useFullscreen`——该模块收编了 requestFullscreen 悬挂与 fullscreenchange 不触发的两个嵌入环境坑）。

```
TableField   = { name, cn?, type?, key?, note? }      // key 如 'PK' / 'UK' / 'FK' / '索引'
TableSpec    = { name, cn?, note?, fields: TableField[] }
DataRelation = { from, to, label? }                   // 表间关系（可选）

<TableTabs title="订单系统表设计" :tables="tables" :relations="relations" />
```

表设计类章节的硬要求：`cn`（中文名）与 `note`（业务说明）逐字段填写，禁止裸罗列。**独立的表关系概览（关键字段 + 外键指向）用 §11 `<TableGraph>`**；本节 `relations` 是就近速查脚注——二者按需取舍，不必都上。

## 11. `<TableGraph>`

表关系图：讲清「多张表怎么连起来」但**不列全量字段**时用它——每张表一张卡（只放关键字段：主键 / 外键 / 唯一 / 状态 / 幂等键…），每条关系画成**连线**（SVG 贝塞尔，箭头指向被引用方，锚点连到**具体字段行**：引用方外键行 → 被引用字段行，线中点标注关系语义）。

**布局用依赖深度分层解决 mermaid 的「乱」**：引用方在左、被引用方在右（列 = 依赖深度），连线只从左往右流；**表多、关系密时替代手写 mermaid erDiagram**（固定排布不会绞线、不需要别名技巧）；表极少且关系单一时 erDiagram 仍可用。

交互：悬停表卡高亮相关连线、无关表卡淡出；悬停/聚焦连线只高亮该条并点亮两端表卡与对应字段行；点击连线跳到被引用表卡并短暂高亮（长页里不用四处找）；右上角**全屏**（含标题栏一起放大，嵌入式环境自动降级为覆盖层，Esc 退出）。

**标签防遮挡**：线中点语义标签按列间空隙宽度估算——放得下走单行直连；放不下先按 CJK 逐字 / 拉丁整词平衡折行（最多两行）；折行仍放不下的长标签随连线改走「绕行走廊」（从列间空隙垂直进出、在画布上下方空档横穿），**标签永不压到表卡上**。

**走廊的通道纪律（2026-10-08 用户反馈「两线重叠难辨指向」后定的）**：走廊线的垂直进出位置**贴列隙边缘**（卡缘 6px 起转弯）并**按通道逐条错开**——与直连线的交叉落在直连线近乎水平/垂直的段落上，形成干净的 90° 十字；若通道落在列隙中部，直连线在那已开始缓弯，两条线会平行贴行、指向难辨。

字段全量归 `<TableTabs>`（§10）——概览用本组件、明细用 TableTabs，关系脚注（`TableTabs.relations`）是就近速查，二者按需取舍不必都上。

```
GraphTable    = { id, name, cn?, note?, fields?: GraphField[] }
GraphField    = { name, cn?, type?, key? }              // TableField 子集：只列关键字段
GraphRelation = { from, to, fromField?, toField?, label?, kind? }
// from = 引用方（持有外键的表），to = 被引用表；一条关系展示为 from.fromField → to.toField
// kind: 'fk'（默认）/ 'logical'（逻辑引用，以徽标/提示提示）

<TableGraph title="订单系统表关系" :tables="tables" :relations="relations" />
```

若仍用 mermaid `erDiagram`（表极少、关系单纯时）：实体在块定义处用别名带中文名（`table_name["table_name · 中文名"] { ... }`，关系行只用裸表名）。页面内 mermaid 图自带「⤢ 放大」浮层（滚轮缩放/拖拽平移/双击 100%/Esc 关闭），复杂图无需额外处理。

## 12. `<EvidenceNote>`

教学片段 ↔ 真实项目快照的证据关联卡。平台原则「教学片段 = 整理 + 教学注释版，不逐行搬真实源码」：本卡把「这一节讲的抽象」与「真实项目里对应的一段真实快照」显式挂起来，`teaching-scope` 声明覆盖什么、不覆盖什么，避免读者误以为片段就是完整源码。`snapshot.kind` 徽标：commit / pr / snippet / doc。

```
ProjectSnapshot = { kind?: 'commit' | 'pr' | 'snippet' | 'doc', title, ref?, description? }

<EvidenceNote
  title="对象池片段 ⇄ 真实项目快照"
  source="本章 2.3 节 CodeWalkthrough 的 Text 对象池片段"
  :snapshot="snapshot"
  teaching-scope="覆盖 Text 对象池的创建与复用；不覆盖字体缓存与字形回退，见 05 章"
/>
```

## 13. `<DebugTable>`

按症状筛选的故障排查表：每行「症状 / 可能原因 / 排查与解决」，顶部按维度（自定义 tag、严重级别）过滤——先按现象 / 模块 / 严重程度收窄再对症下药。纯前端过滤，刷新即还原。

```
DebugRow   = { symptom, cause, fix, severity?: 'info' | 'warn' | 'error', tag? }
DebugFilter = { label, on: 'tag' | 'severity', options: [{ value, label? }] }
severity    = 'info' | 'warn' | 'error'   // 可选：初识过滤的严重级别

<DebugTable title="站点构建疑难排查" :rows="rows" :filters="filters" severity="error" />
```

## 14. `<DiffView>`

**用途**：当讲解要点是「什么变了」（重构、演进、修复、迁移）而周边形状读者已经知道时，用 diff 比整段代码或长篇文字更省注意力——借鉴 show-me skill 的最小视图原则。四种典型裁剪：组件变化、文件布局变化、调用树变化、控制流变化。

**用法**：diff 文本可放课程 `snippets/`（`.diff` 后缀），经迁移器（或手工）内联进 `components` 段数据：

```md
import extractDiff from '../snippets/06-xx.diff?raw'

<DiffView title="导出模块：字节格式化改为复用工具函数"
          filename="src/report/export.ts"
          source="教学整理版（有删节）"
          :diff="extractDiff" />
```

**行为**：兼容标准 unified diff 与手写 +/- 行；`+` 绿底、`-` 红底、`@@`/`---` 元信息弱化；头部显示 +N/−N 统计；一键复制。

**裁剪纪律**：只保留讲清变化所需的行——上下文行超过让读者定位变化所需的量就该删；「diff 里最值得讲的往往是保留不变的行」（见 community 课程 06 章示范）。

## 15. `<HtmlEmbed>`

**用途**：Mermaid 装不下的密集概念——多面板布局、状态对比、需要交互演示的图。来源是 show-me skill 的「HTML 图解」视图（HumanLayer 已用 HTML 取代 Figma 做原型）。

**用法**：自包含 HTML 文件（内联 CSS/JS，**零外部请求**）放课程 `snippets/`，`?raw` 导入后传 `:html`：

```md
import demo from '../snippets/moment-visual-demo.html?raw'

<HtmlEmbed title="六模板同屏对比" :html="demo" height="520px" />
```

**安全边界**：iframe `sandbox="allow-scripts"`（无 allow-same-origin）——图解可带交互脚本，但读不到课程页 DOM/存储。

**「新窗口打开」两条路径**（全部零外部请求，且必有可见反馈）：桌面端经 IPC 让主进程写临时文件并用系统浏览器打开；容器站点走 Blob URL + `window.open`（打开后同步切断 `opener`，用返回值区分「成功」与「被拦」，不用 `noopener` 特性串）。被弹窗拦截器吞掉时页内**覆盖层兜底**放大查看（Esc / 关闭按钮退出）。

**使用纪律**：按需使用——先确认 mermaid/DiffView/FileTree 确实表达不了再写 HTML 图解；一个图解聚焦一个概念。

## 16. `<StateFlow>`

状态机视图：每个状态一张卡，卡内列出它的**出边**（转移目标 + 触发条件）；`current` 高亮当前状态。适合订单状态、任务状态、播放状态一类「有哪些状态、怎么流转」的清单式阅读（比 mermaid 状态图更强调「每个状态能去哪」）。

```
StateNode = { id, label, note?, kind?: 'start' | 'state' | 'end' | 'error' }
StateEdge = { from, to, label? }

<StateFlow title="订单状态机" :states="states" :transitions="transitions" current="paid" />
```

## 17. `<MessageFlow>`

可步进的消息时序图：参与者泳道 + 消息箭头，上一步/下一步逐条高亮（也可点击某一行跳到该步）。适合「谁在什么时候给谁发了什么」的请求链路、事件流、调度时序。`kind: 'return'` 以虚线渲染响应；`from = to` 渲染自调用标记。参与者列较窄时组件内部横向滚动，不与页面滚动打架。

```
MessageParticipant = { id, label, note? }
MessageItem        = { from, to, label, note?, kind?: 'call' | 'return' | 'async' }

<MessageFlow title="一次请求的处理时序" :participants="participants" :messages="messages" />
```

## 18. `<MetricRow>`

指标卡组：一排「数值 + 变化 + 说明」。适合性能 / 规模 / 质量一类量化叙述——比表格直接，一眼看到「从多少变成多少」。`trend`（up/down/flat）只决定箭头，`tone`（good/bad/warn/neutral）决定颜色——**方向与语义分开**：耗时下降与吞吐上升都是 good。

```
MetricItem = { label, value, unit?, delta?, trend?, tone?, note? }

<MetricRow title="服务性能" :items="metrics" />
```

## 19. `<Timeline>`

竖向时间轴：节点 = 时间 + 标题 +（说明），`status` 区分 done（绿）/ active（主色，带光环）/ todo（空心）/ warn（琥珀）。适合版本演进、项目排程、事件序列。

```
TimelineItem = { time, title, note?, status? }

<Timeline title="版本演进" :items="milestones" />
```

## 20. `<CallTree>`

调用树：函数调函数的层层展开（名称 + 可选元信息徽标 + 职责说明），默认展开第一层、其余按需展开——不被无关分支淹没。与 FileTree 的区别：FileTree 陈述「目录里有什么」，CallTree 陈述「一次调用里谁调了谁」。

```
CallNode = { name, note?, meta?, children?, open? }

<CallTree title="buildSite 的调用树" :data="calls" />
```

## 21. `<EndpointList>`

HTTP **接口清单**：默认全折叠——折叠态一行一个端点（方法徽章 / 路径 / 一句话职责 / 权限门槛），点击行才展开契约详情（入参 / 出参关键字段 / 不变量 / 备注）。PRD 接口节的默认组件（替代手写 markdown 端点表）：先回答「有哪些接口、各自干什么」，只对存疑端点下钻，不为细节占版面。

展示程度约定（写内容时可直接依赖）：

- 展开态只放**契约承诺**：入参 / 出参**关键字段** + 不变量 / 校验语义；**不抄全量 DTO**——完整 schema 以 OpenAPI / 代码为准（互链不复制，避免双源漂移）；
- 无详情数据的端点不渲染展开箭头（避免「点了没东西」）；
- `deprecated: true` 的端点整行降透明度 + 路径划线 + 「已退役」徽章——保留可读、不抢视线；
- 顶部方法筛选条（数据中出现的方法才显示；展开状态跨筛选保持）；行右侧 `auth` 徽章表达权限门槛（公开 / 登录 / 权限码）；
- `method` **不限于 HTTP**：非 HTTP 出口同样入清单——WS 推送填 `WS`、事件出口填 `EVENT`、内部调用填 `INTERNAL`（任意字符串，筛选条自动适配，未知方法走中性色徽标）。

```
EndpointParam = { name, in?, type?, required?, desc? }   // in 仅入参用：path / query / body / header
EndpointSpec  = { method, path, summary, auth?, deprecated?, params?, response?, invariants?, note? }

<EndpointList title="订单系统接口清单" :endpoints="endpoints" />
```

与 §9 `<ApiContract>` 的分工：ApiContract 表达**模块级**输入 / 输出契约与不变量（教学向，「谁喂谁、谁能改什么」）；EndpointList 表达 **HTTP 端点清单**（PRD 向，先清单后详情）。按场景取舍，两者可同页共存。

## 22. `<ChangeList>`

PRD / 技术方案「本次改动」节的默认组件：一条改动 = 标题 + 一句话说明 + 涉及模块徽标。`kind` 区分新增（`add`，默认）/ 变更（`change`，琥珀）/ 移除（`remove`，红）；`modules` 以等宽徽标列出涉及的服务或包，扫一眼看出覆盖面。与 DecisionCard 的分工：证的是「改了什么、动了哪几块」用 ChangeList，证的是「为什么这么改」用 DecisionCard。

```
ChangeItem = { title, summary, modules?, kind? }

<ChangeList title="本次功能改动" :items="changes" />
```

## 23. `<RiskList>`

「影响与风险」「已知限制」节的默认组件：每条风险**强制写清「影响」与「当前处置」**，并用 `handled` 标明是否已在本方案内闭环（徽标切换为「本方案已处理」/「待独立处理」）。这一字段是这个组件的存在理由——纯列表会让「明确不修、由独立工作处理」被误读成「已修」。

`severity` 决定左侧色条与徽标色（high 红 / medium 琥珀 / low 中性）；`tag` 是可选环节标签（发布 / 并发 / 缓存…）。

```
RiskItem = { risk, impact, handling, severity?, tag?, handled? }

<RiskList title="已知外部衔接风险" :items="risks" />
```
