# ADR-0008：单工作区导航模型，移除首屏

## 状态

已采纳（2026-11-25）

## 背景

v1.0 的导航是「两级」：启动落在**文档库首页**（工作区卡片列表），点卡片进一个工作区标签，
左树顶部再列一遍工作区作为一级节点（可同时展开多个），标签条里还有一个钉住的「文档库」标签。

实测下来有三个结构性问题：

1. **首屏是多余的一跳**。用户 99% 的时间是「打开应用 → 继续看上次那篇」或「在某工作区里找文件」，
   却每次都要先穿过一屏卡片；而这一屏承载的「工作区管理」（添加 / 移除 / 分享）本身是低频动作。
2. **左树承担了两个职责**。它既是「当前在哪个目录里找东西」（导航），又被要求「同时铺开多个工作区」
   （多根）。后者的代价在窄栏里很明显：每多一层工作区节点就多一层缩进，文件名被挤到看不见；
   且每个展开的根都要扫一遍树。
3. **树跟着标签走**。展开态存在 `TabRecord.expanded` 上，于是切标签时树的折叠状态跟着变。
   这与所有编辑器的直觉相反——树是导航，不该因为「我换了一篇文档看」而重排。

用户明确要求：左侧栏常驻、去掉首屏、设置页也在右侧标签里且左树保持显示、切换工作区不重置标签。

## 决策

1. **移除首屏**：删除「文档库」标签与 `LibraryView`。启动后直接恢复上次的标签；
   没有可恢复的标签时，在当前工作区的落地页开一个预览标签（「落地即内容」）。
2. **侧栏占满标题栏以下的全部高度，标签条只在它右边**：
   布局是「左栏一整列 + 右侧（标签条 + 画布）」，标签条**不横贯全宽**。
   反过来会把目录树切成「标签条上方的空条 + 下方的树」两段，关掉全部标签后
   顶部还留一块空白——「关掉标签树还在」就不只是逻辑成立、画面上也成立。
3. **左栏固定显示单个工作区**：
   - 顶部是**工作区切换器**（当前工作区名 + 点击打开居中弹窗）；
   - 中间是当前工作区的文档树，恒显示；
   - 底部是「最近打开」可折叠区块（跨工作区的文件集合，**不与工作区并列**为一级节点）。
4. **切换工作区只换树，不碰标签**。多个工作区的标签共存；当前标签属于哪个工作区与左树显示谁无关。
   「同时看两个工作区」由标签承担，不由树承担。
5. **树的展开态归属工作区**：`treeExpanded: Record<workspaceId, string[]>`，
   从 `TabRecord` 上移除 `expanded` / `expandedSeeded`。
6. **左栏常驻**：只要有工作区，侧栏就在——包括活动标签是设置页 / 插件页时。
7. **工作区管理走居中弹窗，不是下拉框**：切换器点开 `WorkspaceDialog`（工作区列表 +
   打开文件夹 / 打开文件 / 分享目录 / 移除）。下拉框贴着按钮，条目多了会被窗口边缘裁掉、
   还得自己算翻转；而这里不止「选一个」，还有四个动作，窄条里读起来费劲。
   居中是「一次决策」的语义：选完就关。
8. **双击已打开文档仍激活已有标签**（严格对齐 VSCode）。要同一文件开两个标签用右键
   「在新标签页打开」——VSCode 里也是这条路径。
9. **`Ctrl+1` 是「切换工作区」**，不是「回到工作区首页」。首页只剩「当前库的落地页」
   这一种解释，而它在树里点一下就到；切换工作区反倒是唯一没有键盘通道的高频动作。
10. **右侧必须分两层容器**：`.shell__main`（纵向：标签条 + 内容行）+ `.shell__content`
    （横向：画布 + 本页目录）。合成一层时 `flex-direction: column` 会把大纲排到画布
    下方——它跑到窗口底部，而元素仍然「存在」，纯 HTML 断言看不出来。
11. **树的工具按钮靠右**，工作区名不在树里重复（顶部切换器已有）。
12. **搜索默认只搜当前工作区，可切「全部工作区」**：

- 默认范围由「当前左栏工作区」决定，面板右侧一个按钮轮流切两档；
- 索引**只给当前工作区建**；切到「全部」时才补建其余工作区（`indexAll`）；
- 切到「全部」后结果按工作区分组并带徽标；打开跨库结果时**左栏跟着切过去**
  （`navigateInTab` 里的 `syncSidebarTo`）。

## 原因

1. **首屏的信息密度低于它的成本**：一屏卡片换来的是每次启动多一次点击。
   VSCode 也没有「项目列表」首页——它直接进上次的工作区。
2. **左树的宽度决定了它只能服务一件事**：240px 装不下多根树的缩进。
   用户自己的观察也是「工作区多了左侧会比较乱，每次都要先滚动到目标工作区」。
3. **导航与工作现场必须解耦**：标签是「我在看什么」，树是「我在哪找」。
   把展开态挂在标签上，等于说「换一篇文档看，我的目录也要重排」——这条在实现上是最隐性的错误来源
   （也让「切换工作区」不得不连带处理标签）。
4. **多工作区标签共存已经是既有能力**：`DocRef.key` 带 `workspaceId`，标签天然跨工作区。
   此前只是被「切工作区 = 切标签」的实现方式浪费掉了。
5. **单根是编辑器的默认形态**：VSCode 单文件夹工作区是常态，多根是 `.code-workspace` 的进阶用法。
   我们连多根的必要性都还没有，先不要为它付复杂度。

## 被否方案

| 方案                                                 | 否决原因                                                                                                                                                      |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 保留首屏，但让它变成可选（设置项「启动时显示首页」） | 一个只为少数场景存在的开关，反而让「启动后我看到什么」变成不确定的。要么是首页要么是文档，不要两套。                                                          |
| 工作区全平铺在左树（多根），保留现状                 | 窄栏装不下；每个展开的根都要扫树；「主战场」的视觉层级消失。用户实测反馈也是这个结论。                                                                        |
| 多根模式做成可选（VSCode 的 `.code-workspace`）      | 需要新建「工作区组合」这一层概念与文件格式，而它的真实需求（同时看两个库）已由标签覆盖。等出现「必须同时对照两个库的目录结构」的实际场景再说。                |
| 「最近打开」作为左树的一级节点，与工作区并列         | 它是**跨工作区的文件集合**，不是根。并列会让人以为它也是一个可展开的目录，且它的条目点开后会跳到别的工作区，与「树 = 当前目录」的心智冲突。                   |
| 树展开态继续存在标签上                               | 切标签时树会重排，与所有编辑器不一致；且切工作区时必须连带处理标签的展开态，耦合只会越理越乱。                                                                |
| 设置页 / 插件页做成独立窗口（BrowserWindow）         | 用户说的「独立窗口在右侧」指的是右侧标签页。真开独立窗口要处理多窗口状态同步、关闭顺序、单实例语义——成本远高于收益，而标签已经满足「左树常驻 + 右侧看设置」。 |
| 双击已打开的文档也开新标签                           | 与 VSCode 不一致（用户自己核对后确认 VSCode 是激活已有标签）。要两个标签有明确的右键入口，不该把双击这个最常用的手势改成「总是新建」。                        |
| 标签条横贯全宽（侧栏被切成两段）                     | 树不再是一整列，关掉全部标签后顶部留一条空白；标签条是「右侧工作区」的东西，不该跨到导航列上。                                                                |
| 工作区切换用下拉框                                   | 条目多了被窗口边缘裁掉、要自己算翻转；除「选一个」外还有四个动作，窄条里读不下去。                                                                            |
| 搜索靠结果分组表达范围（不设开关）                   | 用户看不出「我现在搜没搜别的库」，也无法主动缩小范围；且全库索引必须在启动时替永远不打开的库付掉读盘成本。                                                    |
| 搜到别的库的文档时把左栏留在原地                     | 人到了文件却看见另一个库的树，判断不了自己在哪；而不切过去也没有任何收益——标签本来就不受左栏影响。                                                            |

## 后果

**必须**：

- `TabKind` 不再包含 `library`；旧会话里的 library 标签在 `normalizeTab` 阶段被过滤掉。
- `TabRecord` 不再有 `expanded` / `expandedSeeded`；`session.json` 里这两个字段读取时忽略。
- 左栏的 `v-if` 条件只看「有没有工作区」，不看活动标签的类型——设置页 / 插件页下树必须在。
- 标签条必须渲染在 `.shell__main` 里（侧栏的兄弟节点），不能提到 `.shell__body` 之前；
  `verify:app` 用 `getBoundingClientRect` 断言「标签条左边界 ≥ 树右边界」。
- 搜索：`searchIndex.search(text, scope)` 的 scope 由调用方当次决定，不读全局状态；
  其余工作区的索引只在 `onPaletteIndexAll` 里补建，启动时不预建。
- 没有可恢复标签时自动打开当前工作区的落地页；工作区里一篇文档都没有时显示空态引导。

**不再**：

- 不再有「切工作区 = 切标签」这条路径。`switchWorkspace` 只做 `activeWorkspaceId` + 重扫树。
- 不再有左树的工作区展开/折叠（单工作区恒展开；工作区的管理在切换器里）。

**代价**：

- 想「同时对照两个工作区的目录结构」做不到，只能切着看。这是刻意的取舍。
- 树展开态不持久化：重启后每个工作区回到「顶层目录展开」。持久化需要处理「目录已删除 / 工作区已移除」的失效清理，等有实际抱怨再加。
