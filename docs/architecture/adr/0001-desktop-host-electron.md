# ADR-0001：桌面宿主迁移到 Electron

## 状态

已采纳（2026-10-19）

## 背景

桌面宿主原为 Tauri 2（`src-tauri/`，Rust 宿主 + 独立 Rust 服务进程 `docs-studio-serve`）。平台的核心增长路径是**插件生态**，插件作者主体是 Node / 前端开发者。Rust 宿主层对他们构成实质性门槛：写一个插件需要在 Rust 侧登记、调试、出包适配。

同时，平台已有约 5,100 行 Rust（服务进程、分享、git 编排、托盘、自启动），维护这套代码的认知成本全部落在「只有维护者本人」身上，社区无法分担。

## 决策

桌面宿主迁移到 **Electron**；服务层用 `utilityProcess` 运行纯 Node 实现；旧 Tauri 宿主与 Electron 并存一段时间，功能对等后删除。

## 原因

1. **贡献者匹配**：插件作者、壳的开发者、宿主维护者是同一批 Node/前端开发者，一个语言栈。
2. **渲染统一**：壳是 Chromium SPA，Electron 直接复用，不必处理 WebView2 与 Chromium 的差异。
3. **生态与 AI 辅助**：Electron 的文档、示例、社区解答密度远高于 Tauri 的 Node 场景，AI 辅助质量也更高。
4. **服务逻辑去重**：容器端本来就是 Node 实现（MCP、分享），迁移后桌面与容器共用一份，不再维护 Rust/Node 双份语义。
5. **迁移成本可控**：壳（5,848 行 TS）与 deployer（4,218 行）零改动；插件（7,909 行）零改动；仅重写宿主层（约 5,100 行 Rust → 约 2,500–3,000 行 Node）。

## 被否方案

| 方案                                                      | 否决原因                                                                    |
| --------------------------------------------------------- | --------------------------------------------------------------------------- |
| 继续用 Tauri，只把服务改成 Rust 之外的进程                | 插件门槛问题未解决；WebView2 与 Chromium 差异仍需长期兼容，社区贡献意愿受挫 |
| 继续 Tauri 并把 Rust 宿主抽成稳定 ABI，插件用 Node 侧进程 | 仍需维护两层语言与两套调试链路；IPC 桥接层成为新的复杂度热点                |
| 立刻纯 Web 化（PWA + 本地 Node 服务）                     | 丧失托盘 / 自启动 / 文件系统能力；安装体验与「桌面应用」定位不符            |
| 切换到 Neutralino / Wails 等轻量壳                        | 生态与文档密度更差，插件作者门槛与 Tauri 同类问题                           |

## 后果

- **必须**：建立 `packages/desktop`；把 Rust 侧能力（serve / shares / git / autostart / tray）逐项重写并对照验收；数据目录迁移（`com.fanki.docs-studio-viewer` → Electron 路径）。
- **必须**：清理双份实现——Rust `share.rs` 与 deployer `shares.mjs` 合并为 `packages/server` 一份。
- **必须**：功能对等后删除 `src-tauri/`，不得长期双轨。
- **风险**：Electron 安装包体积显著增大（约 +100MB），首次下载体验变差；接受该代价换取生态。
- **风险**：`utilityProcess` 生命周期跟随主进程，与「平台退出不影响服务」冲突——由 `--service` 无窗口模式解决（见方案 §3.3）。
