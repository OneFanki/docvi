# ADR-0004：docvi 架构重构

## 状态

已采纳（2026-10-21）

## 背景

现有 docs-studio 是「一份壳服务四种宿主」的形态（容器站点 / 桌面 app / 单文件 viewer / 临时分享）。这条路线在「多宿主平权」阶段是正确的，但当产品重心转向桌面 app 后，它成为负担：每个 UI 决策都要同时满足另外三个宿主，chrome 只能做折中；壳用 6637 行手写 DOM + 字符串模板（`main.ts` 2866 行 + `host/` 3771 行）承载全部交互，状态与时序锁散落在模块变量里；编辑器能力完全缺失。

同时确定了新的产品方向：**阅读优先的本地 Markdown 文档工作台**，编辑器紧随其后，git / MCP / 分享等能力全部插件化。原「组件包即插件」的边界不足以支撑这个方向。

## 决策

1. **产品更名为 docvi（中文名「页间」）**，以本仓 `main` 为唯一主线持续迭代。
2. **app 为唯一完整宿主**：chrome 用 Vue 3 重写，web 作为次级阅读端只复用 `renderer-core`。
3. **渲染与编辑分家**：`renderer-core` 负责 Markdown → Vue 渲染；`editor` 用 CodeMirror 6 实现「阅读 / 实时预览 / 源码」三模式。
4. **插件三层**：呈现插件（组件 / 主题 / 语法扩展）、沙箱服务插件、受信服务插件；贡献点覆盖命令、菜单、设置、面板。
5. **自研插件容器**，不引入 Cordis 等外部依赖注入框架。
6. **桌面只保留 Electron 一条实现**，与既有决策一致。

## 原因

1. **产品重心已经改变**：阅读体验是差异化壁垒，多宿主平权会持续稀释它。
2. **手写 DOM 是当前最大的工程债**：没有响应式、没有组件边界，时序问题（标签回写、过期渲染、滚动 clamp）反复出现；Vue 化后这些状态可以显式化。
3. **Markdown 保真是核心资产**：156 篇存量文档、26 个组件、声明式数据桥都建立在「原文是事实源」上，因此编辑器必须围绕原文设计，而不是把原文降级为导出格式。
4. **插件生态需要比「组件包」更完整的贡献面**：主题、语法、命令、服务都是可扩展点，只有一层组件注册撑不起开源生态。

## 被否方案

| 方案                                             | 否决原因                                                                                                                             |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------ |
| 在现有手写 DOM 壳上继续增量改造                  | 2866 行 main.ts 与大量隐式状态已互相耦合；继续加功能只会让时序缺陷更难定位                                                           |
| 保留四宿主平权，仅把 app 做漂亮                  | app 的 UI 决策会被站点/viewer 反向约束，这正是当前「布局跳、元素不稳」的根源                                                         |
| Monaco 作为编辑器内核                            | 全局固定行高 + 代码视觉，文档排版只能靠 ViewZone，而 ViewZone 的命中/位置/API 长期不完整；VS Code 自己的 Markdown 预览也不用 Monaco  |
| 块编辑器（ProseMirror/TipTap）做真正的所见即所得 | Markdown 会退化为有损的导入导出格式，frontmatter、自定义标签、源码模式全部变复杂；与「原文是事实源」冲突                             |
| Cordis 作为插件底座                              | 它解决服务依赖与生命周期，但 Electron 的窗口/菜单/协议/托盘是命令式生命周期；且渲染层已有 Vue 响应式，再叠一套依赖追踪是双重心智模型 |
| 依赖 Biome 统一格式化与 lint                     | 实测 2.5.15 不格式化 `.vue` 的 `<template>`（开启 `html.parser.vue` 亦然），模板规则存在缺口                                         |
| 继续维护多个平行仓                               | 大幅改造期同步成本过高；开源后只需一条主线                                                                                           |

## 后果

- **必须**：`renderer-core` 不得 import `electron` / `node:*`，由 `boundaries:check` 守护。
- **必须**：内置组件走原生 Vue 渲染，不再用 custom elements + vue-shim；外部插件保留 `docvi://app/vue-runtime.js` import map 方案。
- **必须**：`docs.config.yaml`（内容协议）与 `<at-kind>`（标签前缀）保持不变，避免 156 篇存量文档迁移。
- **必须**：deployer 与单文件 viewer 冻结，不随新架构维护。
- **代价**：约 6600 行 chrome 逻辑重写（渲染管线 364 行可整段搬），预计 8–10 周全职投入达到功能对齐。
- **代价**：`appId`、数据目录、本地存储键全部变更，旧应用数据需一次性导入（用户确认后执行）。

## 后续修订（2026-10-24）

原始决策里两处判断已被实现结果取代，原文保留、此处记录差异：

1. **web 不是「只复用 renderer-core 的次级阅读端」，而是与桌面同源的第二个完整宿主。**
   容器站点直接伺服 `apps/desktop` 的 web 变体（`vite.web.config.ts` → `dist-web`），
   宿主能力由 `lib/web-host.ts` 把 deployer 的 HTTP 协议接成同一个 `window.docvi`。
   差异只剩「谁提供宿主能力」，chrome 与渲染完全共用。
2. **deployer 不再冻结，它是容器宿主的服务端。** 旧壳、旧桌面宿主（`packages/desktop`）
   与单文件 viewer 已整体删除；deployer 持续维护，负责仓库编排、索引刷新与站点伺服。
3. **「必须：deployer 与单文件 viewer 冻结」这条义务随之失效**，改为：
   `window.docvi` 是两种宿主唯一的能力差异点，渲染层不得按宿主分叉 UI 逻辑。
