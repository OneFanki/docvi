# ADR-0007：单一桌面形态 + 只做通用 Markdown

## 状态

已采纳（2026-11-24）

## 背景

v0.9 之前，docvi 同时维护两种形态：Electron 桌面应用与 Docker 容器站点（`deployer/`）。<!-- scan-allow: 历史记录引用已退役路径 -->
容器版不是桌面的薄包装，它有一套自己的运维面（`/_/admin`）、多仓库编排、分支切换、
索引刷新队列、`OPS_TOKEN` 门禁，以及为它服务的 `web-host.ts` / `web-router.ts`<!-- scan-allow: 历史记录引用已退役路径 -->
适配层。桌面侧还带一整套 git 集成（克隆 / 切分支 / 拉取 / 冲突提示）。

2026-11-24 的评估结论是：**这两块都没有真实用户**。

| 观测项                              | 结果                                                 |
| ----------------------------------- | ---------------------------------------------------- |
| 容器站点部署实例                    | 除作者本机试验外为 0                                 |
| 真实业务仓文档中依赖 git 分支切换的 | 0（作者直接用工作目录）                              |
| 维护成本                            | 双宿主适配层 + deployer 12 个模块 + 各自的门禁与测试 |

同时暴露出一个结构性问题：为了在两种宿主下都成立，渲染层被要求「按 `hostKind` 决定
入口显隐」。这违反了项目自己的硬约束（宿主差异只有一个收口处），并且让每个新功能都要
先回答「容器下怎么办」——而那个问题的真实答案一直是「不做」。

## 决策

1. **桌面是唯一产品形态**：删除 `deployer/`、Dockerfile、compose.yaml、`web-host.ts`、<!-- scan-allow: 历史记录引用已退役路径 -->
   `web-router.ts`、`portal-workspaces.ts`、容器专属 IPC 契约（`hostKind` / `appInfo` /<!-- scan-allow: 历史记录引用已退役路径 -->
   `pluginAssetUrl`）与 `/_/admin` 运维面。
2. **删除 git 集成**：分支模型、`GitBar`、`BranchDialog`、`BranchPicker`、
   `CloneRepoDialog`、`main/git.mjs` 全部移除。**工作区保留**——它承载的是「一个文档目录」，
   与版本控制无关。
3. **保留并加固本地服务**：MCP（AI 读取 / 写入工作区）与局域网临时分享是实际在用的能力，
   它们与「容器部署」是两件事，不随容器一起删。
4. **表达通道只保留通用格式**：见 [ADR-0006](0006-native-markdown-first.md) 的后续变更段。

## 原因

1. **没有用户的功能不是在服务用户**：容器编排的复杂度（多仓库、分支、索引队列、运维鉴权）
   全部为了一个不存在的使用场景。它不是「暂时没人用」，而是作者的文档工作流里根本没有这一环。
2. **双宿主让每个决定都要付两遍成本**：一个新功能要写两套宿主适配、两套测试、两套文档。
   在只有一个真实宿主的情况下，这不是稳健性，是纯开销。
3. **git 与「打开一个文件夹」是两回事**：工作区的价值是「记住我常看的目录」，
   它不需要知道分支。把两者绑在一起曾导致整个工作区注册表建立在 git 仓库模型上，
   删掉 git 后反而更简单（注册表只存根目录）。
4. **保留分享与 MCP 是用户明确要求**：作者把文档临时发给同事看是高频动作，
   而「同事还要装个客户端」是不可接受的摩擦。MCP 则是 AI 读写文档的唯一通道。
5. **单一形态让「不做」变得可说出口**：以前每个功能都要讨论容器下怎么退化；
   现在可以直接回答「不支持」。这比任何架构文档都更能收敛范围。

## 被否方案

| 方案                                         | 否决原因                                                                                                                                                               |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 保留容器版但停止开发（只修 bug）             | 停止开发不等于停止维护：它仍占着双宿主适配层、deployer、独立的门禁与文档。而且「容器下怎么办」这个问题会继续出现在每个新功能的设计讨论里。                             |
| 保留容器版，把它做成真正的团队文档站         | 那需要账号体系、权限、审计、备份、升级路径——是另一个产品的体量。作者的真实需求是「自己写文档 + 临时发给同事看」，后者已由局域网临时分享覆盖。                          |
| 只删容器、保留 git 集成                      | git 集成同样没有使用者，且它把工作区模型绑在仓库模型上（分支 → worktree → 文档根）。保留它会让工作区永远带着「分支」这个多余维度，也让「打开任意文件夹」这条路径更绕。 |
| 把 git 改成可选插件                          | 插件协议目前只承载主题，没有宿主能力扩展点（不注册命令、不注册视图）。为了让一个没人用的功能活下来而扩协议，是把成本从「删代码」转成「长期维护一个扩展点」。           |
| 保留容器版作为「云端部署」选项               | 与「不做云端协作」的非目标冲突（见 README）。云端形态需要的东西（鉴权、多租户、存储抽象）一项都还没做，留个壳只会诱使未来往里填。                                      |
| 删掉本地服务（MCP / 分享），彻底只做本地阅读 | 用户明确说「临时分享反而要留，这是我实际会用的」「本地服务肯定保留，因为需要 MCP 和局域网分享」。删掉会直接砍掉两条在日常使用的路径。                                  |

## 后果

**必须**：

- `window.docvi` 里不出现任何容器痕迹（`hostKind` / `appInfo` / `pluginAssetUrl`）。
- 依赖方向门禁（`check-boundaries.mjs`）继续守护「渲染进程不碰 `node:` / `electron`」——
  这条约束的价值不依赖宿主数量。
- 新增功能时不再需要回答「另一种宿主怎么办」；如果有人说「容器下也要能用」，
  先回到本 ADR。

**不再**：

- 不再引入第二个桌面运行时（Tauri 已于 2026-10-20 删除，旧 Electron 宿主同期退役）。
- 不为「Markdown 表达不了的内容」新增自研声明式组件（见 ADR-0006）。

**代价**：

- 存量会话 / 设置里可能有容器时代留下的字段；读取端一律按「未知字段忽略」处理，
  不做迁移脚本（那些数据对应的功能已不存在）。
- 曾经在容器里读过文档的用户无法继续用同一形态，需要改用桌面版。
