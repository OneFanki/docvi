# ADR-0006：原生 Markdown 优先，组件降级为可选表达

## 状态

已采纳（2026-11-12）

## 背景

docvi 的差异化建立在「任意 Markdown 目录 → 可浏览 / 可搜索 / 可交互」。为此建立了一套自定义渲染组件：作者在 frontmatter 写 `components` 段，正文用 `<at-kind data-key>` 引用，由插件包提供的 Vue 组件渲染。

这套系统本身工作正常，但**推荐策略**出了问题：MCP 的 `initialize` instructions 第一句就是「先 list_components 查看可用组件」，组件文档自称「24 个组件在一切宿主通用」，`component-protocol` skill 把表关系、流程、状态机逐一指派给具体组件。AI 读到这些，写任何文档的第一反应都是套组件。

代价在 2026-11-12 被量化出来：

| 观测项                             | 数值              |
| ---------------------------------- | ----------------- |
| 真实业务仓文档（`data/worktrees`） | 245 篇            |
| 其中使用 `<at-` 组件的             | **11 篇（4.5%）** |
| 本仓内容文档（含组件演示课程）     | 30 篇用组件       |
| 自定义容器语法 `::: ` 全库用量     | **1 处**          |
| 245 篇业务文档里的 mermaid 围栏    | 12 篇             |

组件系统的主要消费者是它自己的演示课程。真实写文档的人几乎不用它，原因是结构性的：用了 `<at-*>` 的文档**离开 docvi 就不再可读**——GitHub 上是裸标签，飞书、语雀、VS Code 预览同理。作者要为一个只在单一工具里成立的表达方式，付出可移植性代价。

同时，组件的核心价值被证伪了一半：`TableGraph` 用了 1032 行实现「依赖深度分层 + 连线锚定字段」，但它存在的理由写着「替代会绞线的 mermaid erDiagram」。实测同一份四表数据，mermaid 加一行 `direction LR` 后高度从 731px 降到 289px，绞线问题消失；而 `mermaid-hover.ts` 早已实现了 erDiagram 的悬停联动。**布局算法才是那 1032 行的价值，而那件事 mermaid 已经做了。**

## 决策

1. **原生 Markdown 与通用扩展是默认表达通道**：GFM 表格 / 任务清单、mermaid 围栏、`::: tip` 类容器、frontmatter 都是推荐写法——它们在任何渲染器里都能读，最坏情况只是退化，不会失去语义。
2. **自定义组件降级为「可选能力」，不再是优先推荐**：保留 `<at-*>` 系统与插件协议，不删除、不冻结，但不再作为写文档的默认选项。
3. **不隐藏、不贬低，但必须声明限制**：MCP 与插件文档**完整暴露**有哪些组件，同时明确说明「不属于通用 Markdown 渲染、只有 docvi 能显示、离开后失去语义」，由 AI 结合用户的实际需求判断用不用。
4. **不做「禁用」开关**：区别在于「默认」与「可选」，不是「允许」与「禁止」。用户明确要求交互式视图时，组件仍是正确选择。
5. **只有「外部标准定的」语法值得持续投优化**：mermaid、GFM、CommonMark 这类有外部规范的输入格式，做视觉优化是净收益（退化后仍然正确）；docvi 自己发明的表达方式不再扩展。

## 原因

1. **可移植性是产品的立身之本**：docvi 的承诺是「把 Markdown 目录变成站点」，不是「把 Markdown 变成只有 docvi 认识的格式」。自定义组件恰恰在破坏这个承诺——它把文档锁进单一工具，与本项目的存在理由相反。
2. **数据证明它不是主路径**：真实业务文档使用率 4.5%，容器语法全库 1 处。为一条 4.5% 的路径付出「默认推荐」的位置，等于让 95% 的普通文档承担复杂度。
3. **默认位置是有成本的**：AI 读到的第一条指令决定它的行为惯性。`instructions` 排在最前的「先看组件」会让 AI 在写一篇简单周报时也去翻组件清单，既慢又容易写出过度设计的内容。
4. **暴露而不推荐，才是诚实的信息结构**：AI 需要知道能力边界（有哪些组件、限制是什么）才能替用户做判断。藏起来会让它在用户明确要「表关系图」时给出更差的方案；当成默认会让它在用户只要一段文字时套上组件。
5. **视觉优化的投入应该收敛到通用语法上**：原生语法的排版缺陷（中英混排、表格宽度、代码块对齐）在所有文档里都存在，修一次全体受益；组件只在 4.5% 的文档里出现，且每次都要求作者先学一套协议。同样的工程投入，前者回报高一个数量级。
6. **mermaid 已经在仓库里且已适配**：`markdown.ts` 拦截 ` ```mermaid ` 围栏，`mermaid-hover.ts` 为 flowchart / erDiagram 实现了节点联动，`mermaid.ts` 提供全屏。它不是新增依赖，是既有能力没被摆到主位。

## 被否方案

| 方案                                          | 否决原因                                                                                                                                                                              |
| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 直接删除组件系统与插件协议                    | 存量 30 篇文档（含全部演示课程）会退化成裸标签；`HtmlEmbed` 这类「HTML 画板」有真实价值，且它本身可移植（独立文件双击就能看）；删除的破坏面远大于收益。                               |
| 保持现状：继续把组件作为默认推荐              | 问题不会自愈。AI 的推荐惯性来自 `instructions` 的措辞，不改措辞就等于继续生产只有 docvi 能读的文档。                                                                                  |
| 加一个「启用/禁用自定义组件」的配置开关       | 把「表达方式选择」降级成「功能开关」，会让用户误以为问题在权限。真实需求是让 AI 知道两种写法的取舍，不是二选一禁掉一个。且开关不解决 AI 不知道「离开 docvi 就失效」这个核心信息缺口。 |
| 把推荐策略写进插件清单（manifest 加字段）     | AI 读的是 MCP `instructions` 与工具描述，不是插件清单。把策略放在一个 AI 启动时读不到的地方，等于没写。                                                                               |
| 为组件做导出转换（导出时还原成原生 Markdown） | 单向有损转换不可逆，且实现成本高于收益：组件数据是结构化 YAML，还原成 Markdown 表格必然丢失信息（如连线锚定的字段行）。与其事后还原，不如一开始就用可移植写法。                       |
| 只改 MCP，不同步技能与插件文档                | 三处口径不一致时，AI 会读到互相矛盾的指令（`instructions` 说可选、skill 说「表关系用 at-table-graph」），最终行为不可预测。口径必须一次改齐。                                         |

## 后果

**必须**：

- MCP `initialize` 的 `instructions` 以「默认写标准 Markdown」开头，组件作为带限制说明的可选能力出现在后面。
- `list_components` / `get_component_docs` 的返回文本必须包含「非通用 Markdown、仅 docvi 渲染」的限制声明，不能只列清单。
- `component-protocol` skill 的「图表达选型」表改为主推 mermaid / 原生语法，组件标注为「需要交互或字段级锚定时才用」。
- `plugins/base/docs/SKILL.md` 与 `docs/architecture/组件协议.md` 顶部声明可移植性边界。
- 新增测试钉住该口径（instructions 必须先提原生 Markdown、必须提到组件仅在 docvi 渲染）。

**不再**：

- 不再为「Markdown 表达不了的内容」新增组件。新需求先问：能否用 mermaid / 表格 / 列表 / HTML 岛表达。
- 不再把组件写进新文档的默认示例。

**代价与保留**：

- 组件系统继续维护（不废弃），插件协议与既有文档不受影响。
- 存量 30 篇文档不做批量重写：碰到才迁，`courses/component-showcase` 保留作为能力展示，但不再作为「推荐写法」的范本。
- `TableGraph` 的退役单独评估（它依赖一次布局质量的实测对照），不在本决策内强制。
