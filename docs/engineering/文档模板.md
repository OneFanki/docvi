# 文档模板

> 复杂功能用四类文档；小改动不建文档。判断标准：**这篇会不会被后来的开发者 / AI 读到并省下时间？**
> 重大跨模块决策另写 ADR（模板见 [ADR 规范](../architecture/adr/README.md)）。

## 一、四类文档

| 文档              | 回答什么                                          | 何时建                         |
| ----------------- | ------------------------------------------------- | ------------------------------ |
| `ARCHITECTURE.md` | 现在是什么结构：模块、依赖方向、公开边界、约束    | 多模块 / 跨边界，随代码同步    |
| `SPEC.md`         | 为什么这样设计 + 怎么验收：问题、决策、边界、验收 | 复杂到需要理清边界时，编码前写 |
| `IMPL.md`         | 技术上怎么实现：算法、数据结构、参数、权衡        | 有值得长期记录的实现细节       |
| `ROADMAP.md`      | 未来要什么：阶段目标、状态、后续                  | 有阶段性规划                   |

**不用 `DESIGN.md`**（与设计规范混淆）。短期专题放 `tech/`，过程计划放 `plans/`（完成移 `plans/archive/`）。

## 二、ARCHITECTURE.md

```markdown
# <功能块名> 架构事实

> 本文是当前已实现事实的真相源；未来计划看 ROADMAP，设计推导看 SPEC。

## 系统快照 ← 当前包含哪些模块（一句话 + 列表）

## 技术栈 ← 框架 / 库 / 关键依赖

## 公开边界 ← 对外入口 / 接口 / 事件

## 架构约束 ← 必须遵守的边界（分层、依赖方向、禁止项）

## 相关文档 ← SPEC / IMPL / ADR / engineering 规范
```

## 三、SPEC.md

```markdown
# <功能块名> 设计推导

## 问题定义 ← 解决什么、范围到哪（含非目标）

## 关键决策 ← 为什么选当前方案（重大跨模块决策另写 ADR）

## 状态 / 数据流 ← 2-3 步说清

## 关键边界 ← 约束、兼容、迁移 / 回滚、风险

## 验收标准

### 需求（SHALL）

- REQ-01：<可验证的陈述>

### 验收场景（GIVEN / WHEN / THEN）

- Scenario: <名称>
  - GIVEN … WHEN … THEN …

### 待确认

- [NEEDS CLARIFICATION] <问题>
```

## 四、IMPL.md

```markdown
# <功能块名> 实现

> 技术实现细节；架构看 ARCHITECTURE，为什么看 SPEC。

## 实现概览 ← 2-3 句

## 关键算法 / 机制 ← 核心算法、公式、数据结构

## 参数与权衡 ← 关键参数、边界、取舍

## 相关文档
```

## 五、ROADMAP.md

```markdown
# <功能块名> 路线图

> 只写未完成与已排期的内容；已完成项删除或移入 ARCHITECTURE。

| 阶段 | 目标 | 状态   | 验收 |
| ---- | ---- | ------ | ---- |
| P0   | …    | 进行中 | …    |
```

## 六、何时不建

- 单文件、无跨模块边界、无算法 → 不建。
- 结论一句话能说清 → 写进对应 ARCHITECTURE 的约束节或踩坑库。
- 宁可少建，不堆冗余：文档的成本是维护，不是写作。

## 变更触发

- 引入新文档类型 → 同步 `docs/engineering/README.md` 与 `AGENTS.md`「按任务读取」表。
