# 界面文案规范

> 界面上的字要么帮用户做决定，要么别写。这份文档定的是「什么该出现在界面上」。

## 判据：这句话用户需要吗

写任何界面文案前先问三件事，有一个答「否」就别写：

1. **它解释了控件看不出来的东西吗？** 控件的效果如果点一下就知道，文字是噪音。
2. **它是给用户的，还是给开发者的？** 实现理由、技术选型、内部约束属于代码注释与工程文档，不属于界面。
3. **删掉它，用户会做错事吗？** 不会就删。

## 三类容易写错的文案

### 1. 实现理由（最常犯）

开发者知道「为什么这么做」很有价值，但那是对**维护者**说的。

| 不写                                                    | 原因                                           |
| ------------------------------------------------------- | ---------------------------------------------- |
| 「代码块固定用 JetBrains Mono：鸿蒙没有公开的等宽版本」 | 字体选型理由，用户只需要知道代码块长什么样     |
| 「MCP 与分享共用同一个进程、端口和令牌」                | 进程模型是架构事实，用户只需要知道关掉会一起停 |
| 「设置保存在 userData/settings.json，可直接编辑」       | 没有提供任何操作，用户看不到也不需要这个路径   |

**判据**：这句话能不能原样搬进代码注释？能，就说明它属于注释。

### 2. 复述控件

按钮写着「折行 / 不折行」，下面再写「折行：长行自动换到下一行」等于说了两遍。

例外：标签只有一两个词、且词义不展开会造成误用时，补一句是有价值的。例如「不折行时超宽内容横向滚动」——它说的是**后果**，按钮名没说。

### 3. 清单与枚举

把 8 个 MCP 工具名列在设置页，等于让用户在一屏里读一份 API 文档。

清单属于文档。界面上只需要指路（「填入 MCP 客户端」），不需要背内容。

## 该留的四类

反过来，以下信息**必须**在界面上，不要以「简洁」为由删掉：

| 类别            | 例子                                                                   |
| --------------- | ---------------------------------------------------------------------- |
| 行为不可预期    | 「改端口会重启服务；端口被占用时会自动顺延」——用户不看就会以为改失败了 |
| 语义非自明      | 「分享是只读链接，读取的是磁盘实时文件」——不看会以为分享了快照         |
| 不可逆 / 有风险 | 「安装包未签名，系统可能提示未知发布者」                               |
| 控件值的含义    | 「0 表示不限」——输入框里写 0 不会自己说明                              |

## 位置规则

- **状态值**放 `row__value`（与标签同一行），它回答「现在是什么」。
- **补充说明**放控件下方一行，它回答「这会怎样」。
- **警告**必须靠近触发它的控件，不要集中到页尾。
- 提示文字不承担导航职责。要指路就给按钮或链接。

## 自检

改完界面前扫一遍新增的每一句：

```
这句删掉，用户会不会做错事？
  → 会：留下，并确认它讲的是「会发生什么」而不是「为什么这么实现」
  → 不会：删掉
```
