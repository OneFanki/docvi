# 渲染层性能基线与埋点

> 建立：2026-11-18 ｜ 数据来自无头 Electron 跑真实构建产物（`apps/desktop/out`）的实测

## 一、当前基线

测量环境：1440×900、deviceScaleFactor 1、无头 Electron 44、Windows。

| 场景                      | 结果                                                        | 判据                            |
| ------------------------- | ----------------------------------------------------------- | ------------------------------- |
| 连续输入 42 字符          | 帧间隔均值 16.6ms，p95 19.7ms，最长 21ms，**0 次 longtask** | 满 60fps                        |
| 长文档滚动 2 秒           | 均值 16.7ms，p95 17ms，超 33ms 的帧 0–2 个                  | 满 60fps                        |
| 切到实时预览（已缓存）    | 22–27ms                                                     | 首次 124–148ms（含 chunk 加载） |
| 打开 451 块文档（阅读态） | 正文可见 ~40ms                                              | 含高亮与图表                    |
| 打开 1201 块文档          | 正文可见 ~110ms                                             | 同上                            |
| 启动到可交互              | ~1100ms（从进程启动算）                                     | 含主进程启动                    |

**结论：编辑器（CodeMirror + Live Preview 装饰）不是瓶颈，无需优化。** 唯一的规模相关项是「切回阅读」随块数线性增长（约 0.07ms/块），1351 块时约 100ms，属于该体量的合理代价。

## 二、被实测否掉的优化假设

写下这些是为了避免以后重复投入——它们看起来都很像瓶颈，但都不是。

| 假设                             | 实测                                                                                                            | 结论                       |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------- | -------------------------- |
| `:has()` + 属性子串选择器太贵    | 删掉全部 `:has` 规则：136ms → 128ms                                                                             | 只占 6%，不是主因          |
| `reportScroll` 强制同步布局      | 451 块全程 `getBoundingClientRect` 只调 **2 次**、0ms                                                           | 假设不成立                 |
| EditorView chunk 1.16MB 拖慢切换 | 首次 148ms、之后 22ms；chunk 内不含 mermaid 实体代码（它本就动态导入）                                          | 首次成本，非持续成本       |
| markdown 解析慢                  | HTML 落地 7–13ms（451 块）                                                                                      | 不是瓶颈                   |
| 主 chunk 1.83MB 拖慢启动         | 可交互 1098ms，且 Vite 已 tree-shake；`renderer-core` 的桶文件把 markdown 管线带进 EditorView，但实测无启动拖累 | 不值得为假设收益付重构成本 |

## 三、埋点设计

### 默认关闭

设置项 `perfTracing` 默认 `false`。关闭时 `lib/perf.ts` 连 `PerformanceObserver` 都不建，运行时开销严格为零。

理由：埋点只在出卡顿时有价值，而绝大多数用户永远不需要诊断。为用户不理解的东西付后台代价，不该是默认行为。

### 开启后也不常写盘

两层收敛：

1. **采样先进内存**：`PERF_BUFFER_LIMIT`（200 条）的环形缓冲，不触盘。
2. **只在触发阈值时上报**：长任务 ≥ `PERF_LONG_TASK_MS`（50ms）或显式计时 ≥ `PERF_SLOW_OP_MS`（200ms）才推给主进程。同一会话推过的记录用 `WeakSet` 标记，不重复上报。

净效果：开着埋点时，一次正常使用可能一条都不写。

### 落盘有硬上限

主进程 `perf-log.ts`：

- 内存与文件都受 `PERF_KEPT_LIMIT`（500 条）约束；
- 文件受 `PERF_FILE_MAX_BYTES`（128KB）约束，超了从**最旧一端**丢（诊断看的是最近的现场）；
- 200ms 攒批写一次（`FLUSH_DELAY_MS`），避免一次卡顿的连发记录触发几十次写盘；退出前 `flushPerfSamples()` 兜底。

文件位置：`<dataDir>/cache/perf.json`。放 `cache/` 而非数据根——可随时删除的运行现场，不是需要备份的用户数据。

### 不含本机信息

`normalizeSample` 强制约束：`scene` ≤60 字符、`detail` ≤6 个键且值 ≤40 字符、非有限数归零（否则 JSON 写 null）、小数保留一位。

`detail` 只放**规模**（块数、节点数）不放路径——埋点文件可能被用户贴进 issue，绝对路径会泄露目录结构。

## 四、扩展埋点

加新场景用 `startPerfTimer`：

```ts
const done = startPerfTimer('switch', 'switch:read', () => ({ blocks: 451 }))
// ... 做完
done()
```

`detail` 传函数而不是对象：它是收尾时才求值的，可以读那时才存在的状态（如已挂载的 DOM 规模）。

新增 `PerfKind` 要在 `packages/shared/src/perf.ts` 里加，并按需决定它走哪个阈值。

## 五、验收

- 单测 `tests/main/perf-limits.test.mjs`（17 条）：上限、裁剪方向、非有限数、超长文本。
- 端到端 `pnpm docvi:build` 后用无头 Electron 走真实 UI：默认不写盘 → 点开关 → 长文渲染 → 校验文件存在、大小 ≤128KB、条数 ≤500、不含本机路径 → 关开关后不再新增。

端到端必须**点真实 UI**：直接调 `window.docvi.settingsWrite` 绕过渲染层的采集切换，会把「开关不生效」这个真 bug 掩盖掉（本功能开发时确实踩到了，见踩坑库）。
